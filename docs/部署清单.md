# 部署清单（合并/上线顺序）

> 对齐架构图后的完整部署顺序。区域固定 `ap-northeast-1`。
> **首次必须按下面顺序手动部署**；全部就绪后，合并到 `main` 由 CI 保持同步。
> ECS Go 栈现在也在 CI 里（`deploy.yml` 的 `deploy-ecs` job，Go/模板变更时自动构建镜像+部署），
> 但**首次前提**是第 1 步的 `github-oidc` 栈已用**新版**重部署（含 `ecs-boundary` + ecr/ecs 权限）。

## 关键依赖（先理解再动手）

- **Lambda 是薄代理**，`/api/*` 生产流量转发到 `GO_API_URL = http://go-api-alb.<stack>.internal`（私有 DNS → Internal ALB → ECS Canary）。旧 Cloud Map 直连地址只用于迁移/回退。
  → **ECS Go 栈没起来之前，`/api/*` 会 502**（`/health`、`/` 正常）。所以主栈之后必须尽快部署 ECS 栈。
- **主栈导出**被 ECS 栈 `Fn::ImportValue` 消费 → **主栈必须先于 ECS 栈**。
- **前端用 `apps/web/public/_worker.js`（Cloudflare Pages 高级模式）** 把 `/api/*` 同源代理到 `API_ORIGIN` 并注入 Basic Auth（凭据只在 Pages 环境变量里，前端不暴露）。→ **Pages 项目必须设 3 个环境变量** `API_ORIGIN`（后端入口，填 API Gateway 默认地址或 `https://api.faithcal.xyz`）、`BASIC_AUTH_USER`、`BASIC_AUTH_PASSWORD`；**改环境变量后要重新部署一次**才生效（Pages env 只对新部署生效）。不再用 `_redirects`（它无法代理外部源）。
- **合并到 `main` 会自动触发** `deploy.yml`（主栈 Lambda + **ECS Go 栈**）和 `deploy-web.yml`（Pages）。首次因为主栈/ECS 有先后依赖 + ECR 鸡蛋问题，`deploy.yml` 已内建处理（`deploy-ecs` needs 主栈、首跑先 DesiredCount=0 建 ECR 再推镜像）；**但前提是第 1 步 bootstrap 已就绪**。稳妥起见首次也可按下面手动跑一遍。

## Go Canary 上线前 bootstrap（必须先执行）

ECS 原生 Canary 新增了 Infrastructure Role、Lifecycle Hook Invoke Role 和 Green Validation Lambda Role。先用本地管理员身份更新权限边界和 GitHub OIDC DeployRole，再允许 CI 部署业务栈：

```bash
aws cloudformation deploy \
  --region ap-northeast-1 \
  --stack-name github-oidc-deployer \
  --capabilities CAPABILITY_NAMED_IAM \
  --template-file infra/github-oidc.yaml \
  --parameter-overrides \
    GitHubOrg=PrettyKing \
    GitHubRepo=github-repositories-fllow \
    DeployStackName=github-repositories-fllow \
    DeployRegion=ap-northeast-1 \
    CreateOidcProvider=true
```

该步骤扩展项目权限边界，允许 ECS Infrastructure Role 管理项目 ALB、ECS 调用 Green Validation Lambda，并允许 GitHub DeployRole 将对应角色传给 `ecs.amazonaws.com` / `lambda.amazonaws.com`。不要先推送业务改动，否则 CI 会在创建基础设施角色或 PassRole 时失败。

首次迁移由流水线自动分三段完成：

1. `deploy-ecs` 创建第二 Target Group、Listener Rule、私有 ALB DNS，暂不启用 Canary。
2. `activate-go-canary-route` 使用 Lambda 的 10% Canary 把代理切到 Internal ALB。
3. `deploy-ecs-canary` 发布新 Go 镜像，执行 10%/10 分钟 ECS Canary 和告警回滚。

## AI Ops Console 快速部署

AI Ops Console 是独立 React 应用，不是 MCP 页面。首次上线遵循：

1. 先用最新版 `infra/github-oidc.yaml` 更新 bootstrap，确保 DeployRole 具备 Cognito 和 Console AWS 栈权限。
2. 确认 messaging、observability、aiops 主体栈已部署，Console API 会读取这些栈的 Topic、DLQ、Canary、日志组、DeploymentGroup 和 Incident 表。
3. 在 GitHub 设置 `AIOPS_ADMIN_EMAIL`，值为接收 Cognito 临时密码的管理员邮箱。
4. 手动触发 `Deploy AI Ops Admin Console` workflow，或将相关文件合并到 `main`。
5. 从 workflow Summary 获取 Cloudflare Pages Console URL，使用邮件中的临时密码登录并设置正式密码/MFA。

部署流水线会构建 `apps/aiops-console/dist`，再根据 CloudFormation 输出写入生产 `config.js`。生产配置固定 `demoMode=false`，浏览器只通过 Cognito JWT 调用 Console HTTP API。

本地界面验收：

```bash
pnpm --filter aiops-console dev
# http://127.0.0.1:4322/
```

本地预览不会访问 AWS。MCP 仍独立运行：

```bash
pnpm --filter aiops-mcp dev
```

MCP 使用 stdio，没有浏览器页面或监听端口。

## 步骤

### 1）Bootstrap（admin，一次性）
- [ ] 部署 OIDC + 权限边界栈：
  ```bash
  aws cloudformation deploy --region ap-northeast-1 \
    --stack-name github-oidc-deployer --capabilities CAPABILITY_NAMED_IAM \
    --template-file infra/github-oidc.yaml \
    --parameter-overrides GitHubOrg=PrettyKing GitHubRepo=github-repositories-fllow
  ```
- [ ] 取输出 `DeployRoleArn` → 存 GitHub Secret `AWS_DEPLOY_ROLE_ARN`
- [ ] 确认输出里有 `LambdaBoundaryArn` + `EcsBoundaryArn`（供主栈/ECS 栈引用）

### 2）主栈（Lambda 薄代理 + VPC + Aurora + secrets）
- [ ] `sam deploy`（读 `samconfig.toml`，栈名 `github-repositories-fllow`）
- [ ] 取 Basic Auth 密码：
  ```bash
  aws secretsmanager get-secret-value --region ap-northeast-1 \
    --secret-id <AuthSecretArn> --query SecretString --output text
  ```
- [ ] （可选）填 OpenRouter key 再重部署一次：
  ```bash
  aws secretsmanager put-secret-value --region ap-northeast-1 \
    --secret-id <stack>/openrouter --secret-string '{"apiKey":"<你的key>"}'
  # 然后重新 sam deploy 让 Lambda env 重新 resolve
  ```
- [ ] 此时 `GET /health` 应 200；`/api/*` 会 502（正常，ECS 还没起）

### 3）ECS Go 栈（唯一连库方）—— 合并到 main 后由 `deploy-ecs` job 自动完成
> CI 已自动化：`deploy.yml` 会在 Go/`ecs-fargate.yaml` 变更时构建 arm64 镜像、推 ECR、部署 ECS，
> 首跑自动处理「先建 ECR(DesiredCount=0) → 推镜像 → DesiredCount=1」。**下面是等价的手动命令**（想先手动验证时用）：
- [ ] 先建栈但服务规模 0：
  ```bash
  sam deploy --template-file infra/ecs-fargate.yaml \
    --stack-name github-repositories-fllow-ecs \
    --capabilities CAPABILITY_NAMED_IAM --resolve-s3 \
    --parameter-overrides DesiredCount=0
  ```
- [ ] 构建并推 arm64 镜像（仓库 URI 见栈输出 `EcrRepositoryUri`）：
  ```bash
  aws ecr get-login-password --region ap-northeast-1 | docker login --username AWS --password-stdin <registry>
  docker build --platform linux/arm64 -t <EcrRepositoryUri>:v1 apps/go-api
  docker push <EcrRepositoryUri>:v1
  ```
- [ ] 拉起服务：
  ```bash
  sam deploy --template-file infra/ecs-fargate.yaml \
    --stack-name github-repositories-fllow-ecs \
    --capabilities CAPABILITY_NAMED_IAM --resolve-s3 \
    --parameter-overrides DesiredCount=1 ImageTag=v1
  ```
- [ ] 等 ECS 服务 stable，并确认最新 Service Deployment 的 `strategy=CANARY`、`status=SUCCESSFUL`
- [ ] 确认 Production Listener `:80` 与 Green 专用 Test Listener `:8081` 都存在。
- [ ] Test Listener 仅放行 `CanaryHookSecurityGroup`，公网和业务 Lambda 均不能访问。
- [ ] 最新 Service Deployment 的 `POST_TEST_TRAFFIC_SHIFT` Hook 为 `SUCCEEDED`，日志显示 `/health=200`、`/api/stats=200`。
- [ ] 用故障镜像演练其中一个接口非 200，确认 Hook `FAILED` 且生产流量保持/回滚到 Blue。

### 4）验证后端（走 API Gateway 默认地址）
- [ ] `GET /health` → 200
- [ ] `GET /api/users`（带 Basic Auth）→ `[]` 或数据（说明 Lambda→私有 DNS→Internal ALB→Go→Aurora 全通）
- [ ] `GET /api/profile/PrettyKing` → 含 `introduction`（有 key 是 LLM，没 key 是模板）

### 5）API 自定义域名 `api.faithcal.xyz`（前端依赖它）
- [ ] 申请 ACM 证书（**ap-northeast-1**，DNS 校验）：
  ```bash
  aws acm request-certificate --region ap-northeast-1 \
    --domain-name api.faithcal.xyz --validation-method DNS
  ```
- [ ] 取校验用 CNAME（`aws acm describe-certificate ...`），写进 Cloudflare：
  ```bash
  CF_API_TOKEN=... CF_ZONE_ID=... \
    scripts/cloudflare-upsert-dns.sh CNAME <校验name> <校验value> false
  ```
- [ ] 证书 issued 后，主栈带域名重部署：
  ```bash
  sam deploy --parameter-overrides \
    ApiDomainName=api.faithcal.xyz ApiCertificateArn=<证书ARN> \
    'CorsOrigin="*"'
  ```
- [ ] 把 `api.faithcal.xyz` 指向栈输出 `ApiDomainTarget`（**DNS-only 灰云**）：
  ```bash
  CF_API_TOKEN=... CF_ZONE_ID=... \
    scripts/cloudflare-upsert-dns.sh CNAME api.faithcal.xyz <ApiDomainTarget> false
  ```

### 6）前端 Cloudflare Pages `app.faithcal.xyz`
- [ ] 配 GitHub Secret `CLOUDFLARE_API_TOKEN`（含 **Account > Pages > Edit** + **Zone > DNS > Edit**）+ `CLOUDFLARE_ACCOUNT_ID`
- [ ] 首次可本地推一版，或合并触发 `deploy-web.yml`（会自动 `pages project create github-repositories-fllow-web` 再 `pages deploy out`）：
  ```bash
  pnpm --filter web build   # 产出 apps/web/out（含 _worker.js）
  npx --yes wrangler@3 pages deploy apps/web/out --project-name=github-repositories-fllow-web --branch=main
  ```
- [ ] **在 Pages 项目设 3 个环境变量**（生产环境）并**重新部署**一次使其生效：
  ```
  API_ORIGIN=https://<execute-api 默认地址 或 api.faithcal.xyz>
  BASIC_AUTH_USER=<AuthSecret.username>
  BASIC_AUTH_PASSWORD=<AuthSecret.password>
  ```
- [ ] Pages 项目绑定自定义域名 `app.faithcal.xyz`（会自动在 zone 建 proxied CNAME）
- [ ] 打开 `https://app.faithcal.xyz`：加账户/统计/profile 全通（`/api` 由 `_worker.js` 同源代理注入 Basic Auth 转发到 `API_ORIGIN`）

### 7）（可选）启用 PR 预览（分权安全 + 共享 ALB + 每 PR 前端界面）
> ⚠️ 前置：主栈须**先部署好**（预览用它的 `VpcId`/`PublicSubnet`/`PublicSubnet2` 导出跨 2 AZ + `AuthSecret`）。
> ⚠️ 成本：共享 ALB 常驻计费（~$16/mo，无 PR 时也在）；不启用就没有这项。
> ⚠️ **workflow 逻辑必须在 base 分支(`main`)**：`pull_request_target` 只从 main 加载 `preview-*.yml`，改预览流水线要先推 main 才生效（改 `pr-preview.yaml` 的 IAM 则重部署 bootstrap 栈即时生效）。

- [ ] 部署 bootstrap 栈 `infra/pr-preview.yaml`（admin，一次性）：三角色（Ops/Build/Runtime）+ 预览 ECR + **共享 ALB** + Cloudflare 密钥占位。**OpsRole 已含**：ECR push、CDK 资产桶 S3、`logs:TagResource`、`cloudformation:DescribeStacks`(主栈)、`GetSecretValue`(AuthSecret)。
  ```bash
  aws cloudformation deploy --region ap-northeast-1 \
    --stack-name github-repositories-fllow-pr-preview --capabilities CAPABILITY_NAMED_IAM \
    --template-file infra/pr-preview.yaml \
    --parameter-overrides GitHubOrg=PrettyKing GitHubRepo=github-repositories-fllow
  ```
- [ ] **`cdk bootstrap`（每 PR 栈用 CDK，仍需资产桶）**——`cdk.json` 的 app 要求 context，传占位即可：
  ```bash
  cd infra/cdk && npm install
  npx cdk bootstrap -c prNumber=1 -c imageUri=x \
    -c runtimeRoleArn=arn:aws:iam::<acct>:role/x aws://<acct>/ap-northeast-1
  ```
- [ ] 填 Cloudflare 密钥（token 需 **Zone DNS Edit**；前端预览另用 GitHub Secret `CLOUDFLARE_API_TOKEN` 的 Pages 权限）：
  ```bash
  aws secretsmanager put-secret-value --region ap-northeast-1 \
    --secret-id github-repositories-fllow/cloudflare \
    --secret-string '{"apiToken":"...","zoneId":"..."}'
  ```
- [ ] 把栈输出 `OpsRoleArn` 存 GitHub Secret `AWS_PR_PREVIEW_OPS_ROLE_ARN`
- [ ] 开 PR 即触发 `preview-deploy.yml`（`pull_request_target`，fork PR 被 same-repo guard 挡）；关闭触发 `preview-destroy.yml`；每晚 `preview-reconcile.yml` 兜底清扫
- **每 PR 干了什么**：GitHub Actions `buildx` 打 arm64 镜像推 ECR（账号 CodeBuild 配额 0，改在 Actions 构建）→ **CDK** 建每 PR 栈（Fargate `go-api` + postgres 边车，挂共享 ALB 的 Host 路由）→ Cloudflare 写 `api-pr-<n>`（DNS-only）→ 建**每 PR 独立 Pages 项目** `…-pr-<n>-web`（env 指向该 PR 后端）→ 部署 PR 前端 → 挂 proxied 自定义域名 `pr-<n>.faithcal.xyz`。
- **预览地址**：🌐 前端 `https://pr-<n>.faithcal.xyz`、API `http://api-pr-<n>.faithcal.xyz`（写进 PR 评论 + Summary + Environment）。
- 本地体验 CDK：`cd infra/cdk && npm install && npx cdk synth -c prNumber=1 -c imageUri=x -c runtimeRoleArn=arn:...:role/r`

## 合并后的 CI（就绪后自动保持同步）

- push/merge 到 `main` → `deploy.yml`（主栈 Lambda + **ECS Go 栈**，ECS 仅在 `apps/go-api`/`infra/ecs-fargate.yaml` 变更时）+ `deploy-web.yml`（Pages，仅 `apps/web`/`packages/ui` 变更时）
- `deploy.yml` 的 `deploy-ecs` job：`needs: deploy`（主栈先行）→ 首跑建 ECR → `docker buildx` 打 arm64 推镜像 → `cloudformation deploy` 更新服务 → 等 stable。镜像 tag = commit SHA。

## 完整拆栈（验收后省钱，**严格逆序**，本次实战验证过）

> 依赖关系：每 PR 栈/ECS/pr-preview 都 `ImportValue` 主栈导出 → 主栈必须最后于它们；
> `github-oidc-deployer` 持有主栈 Lambda 角色引用的**权限边界** → 必须最后删（主栈角色先释放）。

```bash
R=ap-northeast-1
# 1) 先清 Cloudflare（趁 CloudflareSecret 还在，读 token 删本项目 DNS + Pages 项目）
#    - DNS：api-pr-<n> / app.faithcal.xyz / pr-<n>（按 id 精确删，勿碰同 zone 其它项目）
#    - Pages：先摘自定义域名再删项目 …-web 与 …-pr-<n>-web
# 2) 每 PR 预览栈（若有）：cd infra/cdk && npx cdk destroy github-repositories-fllow-pr-<n> --force -c prNumber=<n> ...
aws cloudformation delete-stack --stack-name github-repositories-fllow-pr-<n> --region $R   # 每 PR 栈
aws cloudformation delete-stack --stack-name github-repositories-fllow-ecs --region $R       # ECS Go（内网 ALB+Fargate+CloudMap）
aws cloudformation delete-stack --stack-name github-repositories-fllow-pr-preview --region $R # 预览基础设施（共享 ALB+ECR+OpsRole+CFSecret）
aws cloudformation delete-stack --stack-name github-repositories-fllow --region $R           # 主栈（Aurora+NAT+Lambda+APIGW+VPC）
# 3) CDK 引导：先清空资产桶再删栈
aws s3 rm s3://cdk-hnb659fds-assets-<acct>-$R --recursive --region $R
aws cloudformation delete-stack --stack-name CDKToolkit --region $R
# 4) 最后删 CI 引导（含权限边界/OIDC provider/部署角色）
aws cloudformation delete-stack --stack-name github-oidc-deployer --region $R
# 数据库/ECR 都是 DeletionPolicy: Delete + ECR EmptyOnDelete，不留快照/镜像。
# 每步 delete 后 describe-stacks 轮询到 “does not exist” 再删下一个（有依赖导出）。
```

> 拆完可选：删 GitHub 仓库 Secrets（`AWS_DEPLOY_ROLE_ARN`/`AWS_PR_PREVIEW_OPS_ROLE_ARN` 指向已删角色；`CLOUDFLARE_*` 视需要保留）。
